# Classic -> flexi mask migration test suite

Regression tests for the classic (pre-flexi) to flexi mask migration in
`src/develop/masks/migrate_legacy.c` (entry point
`dt_masks_migrate_classic_to_flexi`).

## What's here

- `gen_xmp.py` — generates the XMPs under `xmps/` directly from the classic
  `dt_develop_blend_params_t` (v14) struct layout and the classic mask-point
  structs, i.e. without going through the darktable UI. Each XMP loads as a
  genuinely classic (non-flexi) history stack, so rendering it with any
  current darktable-cli build forces the classic->flexi migration to run.
- `images/Sweep_sRGB_Linear_Half_Zip_01.tif` — the single input image all
  scenarios render against. Downscaled to 960x540 (Lanczos, 16-bit and the
  original linear-RGB ICC profile preserved) from the original 1920x1080 to
  keep the fixture small and the suite fast; export target below is scaled
  down to match (400x225, was 800x450). Nothing about mask/shape rendering
  cares about the source resolution, so this doesn't affect what the suite
  actually tests.
- `xmps/` — the 29 generated scenarios (checked in; re-run `gen_xmp.py` to
  regenerate them if the generator changes — they are deterministic).
- `expected/` — checked-in reference PNGs, one per scenario, rendered with
  a known-good migrated build.
- `baselines/` — two reference XMPs used only by `verify_effect.sh` (see
  below): the exposure module fully disabled, and fully enabled with a
  uniform (unmasked) blend. Also generated by `gen_xmp.py`.
- `run.sh` — the driver, see below.
- `verify_effect.sh` — the mask-effect sanity check, see below.

Every scenario runs a single `exposure` module bump of **+5EV** through its
mask (see `EXPOSURE_PARAMS_HEX` in `gen_xmp.py`) — large enough that a real
mask's shape and a constant/no-op mask are unmistakably different in the
rendered PNG, rather than a faint bump that's hard to tell apart from "no
mask at all" by eye.

## Scenario coverage

Two shapes (a large circle, a partially overlapping square) combined with
the four classic drawn-mask operators (union/intersection/difference/
exclusion), per-shape and group-level polarity invert, 1-3 parametric
channels with a taper-in 0-30% / taper-off 50-80% curve, and
`DEVELOP_COMBINE_INCL` crossed with `DEVELOP_COMBINE_INV`/
`DEVELOP_COMBINE_MASKS_POS`:

- `A*` — drawn only, varying operator + invert
- `B*` — parametric only, varying channel count + polarity
- `C*` — drawn AND parametric combined
- `D*`/`E*` — `DEVELOP_COMBINE_INCL` combinations, including the exact
  state produced by clicking "invert all channel polarities" then deleting
  the drawn mask
- `F*` — `DEVELOP_COMBINE_INCL` with drawn content and every channel of
  the colorspace active at once (`INV=0`/`INV=1`)
- `G*` — bare `DEVELOP_MASK_ENABLED` (classic "uniform", no drawn/
  parametric/raster bit at all), which migration normalizes to
  `ENABLED|FLEXI`
- `H*` — per-shape opacity + refinement, carried over unchanged by migration
- `I*` - two members over the same overlapping circle and square, both
  carrying the same non-union operator (`I1` intersection, `I2` sum).
  Classic applies each member's operator once per member, so migration has
  to give each member its own group; merged into one, the pair renders
  differently (see `build_operator_chain_scenarios()` in `gen_xmp.py`).

- `J*` — mask refinement at each of its three scopes. The same fields
  (details / feathering / blur / contrast / brightness) apply at three
  different points in the fold and are not interchangeable: **element**
  (`dt_masks_point_group_t.refinement`, `enabled=1`) on one member's own mask
  before it composites; **group** (same storage, `enabled=2`, broadcast onto
  every member of the run) once on the group's finished sub-mask; **global**
  (`dt_develop_blend_params_t.blur_radius` etc.) once on the whole mask after
  every group has composited. Blur is the probe: purely spatial, no guide
  image or scharr buffer needed, and order-sensitive, so blur-then-union and
  union-then-blur are distinguishable images.

  Two things about this set are easy to get wrong and are worth knowing:

  - **`J1` and `J5` render identically, on purpose.** With a single group,
    the base group seeds the accumulator directly, so "this group's finished
    sub-mask" and "the whole mask" are the same buffer, and group scope
    collapses onto global scope. `J7`/`J8` are the pair that actually pins
    group scope down: two groups, refinement on the first one only, at group
    scope vs global scope. Those differ by ~17k pixels.
  - **Element and group scope cannot coexist on one run.** Setting group
    scope broadcasts one refinement onto every member, overwriting their
    element ones, so a mixed run is not a state the GUI can produce. A case
    that marks the head `ELEMENT` and the tail `GROUP` tests nothing: group
    scope is read off the run head, so the tail's marking is simply inert.

  `J2` vs `J3` (element refinement on the run head vs on a non-head member)
  checks that the renderer applies each member's element refinement to that
  member alone: reading the head's for the whole group would both spread the
  head's refinement across it and drop every other member's.

Not exhaustive by design — a sufficiently large cross-section to catch
inconsistencies, not every permutation.

### Do these tests actually fail?

They were validated by mutation, not by assuming a green run means coverage:

| Mutation to `_group_get_mask_roi_flexi` | Caught by |
|---|---|
| group-scope refinement never applied | `J5`, `J6`, `J7` |
| run head's refinement read unconditionally (the historical leak) | `J2`, `J4`, `H1`, `H2` |

Both mutations left the other 30+ scenarios green, so the failures are
attributable rather than blanket. Worth repeating for any new case: a
reference image generated from current behaviour proves nothing until you have
seen it go red.

## Running

```
./run.sh
```

Renders every scenario with the current `darktable-cli` (or `$DARKTABLE_CLI`)
and does an exact pixel-diff (`../integration/count-diff-pixels`, not a
perceptual delta-E) against the matching `expected/*.png`. This is the
normal regression mode — any exact-match failure here means either the
migration logic changed behavior or a real rendering regression was
introduced.

```
./run.sh --pristine /path/to/pristine/darktable-cli
```

Re-runs the original validation methodology instead: renders each scenario
with both the given pristine binary (a build with the migration's effects
reverted, so classic mode renders un-migrated) and the current binary, and
diffs the two directly. Only needed when re-validating the migration
itself against a from-scratch pristine build — much slower (two renders
per scenario) and not needed for ordinary regression testing.

```
./verify_effect.sh
```

Confirms every scenario's mask actually does something, rather than
silently being a no-op that happens to still pixel-match `expected/`
(e.g. a shape mask that's empty because of a bad operator combination).
Renders each scenario alongside the two `baselines/` references and
exact-diffs against both:

- **PARTIAL** (differs from both) — a real, spatially-varying mask.
  Expected for every `A`/`B`/`C` scenario.
- **CONSTANT_ZERO** / **CONSTANT_FULL** (bit-identical to one reference) —
  a flat opacity with no shape at all. Expected *only* for the `D`/`E`
  series, which exist specifically to probe `DEVELOP_COMBINE_INCL`'s
  constant-collapse behavior in classic's `blendif_*_make_mask()` — see
  the per-scenario comments in `gen_xmp.py`. This is itself a stronger
  check than a pixel-diff against `expected/`: it confirms the constant is
  bit-exact (opacity exactly 0.0 or exactly full), not merely close.

Each scenario has an expected classification hard-coded in
`verify_effect.sh` (`expected_classification()`); a mismatch fails the
script. Update that table only alongside a matching, verified change to
`migrate_legacy.c` or to a scenario's own mask configuration — never to
make a failing check pass.

## Updating `expected/`

If a scenario's rendering intentionally changes (e.g. a real bug fix in
migration or rendering logic, verified some other way first), regenerate
its reference:

```
darktable-cli --width 400 --height 225 --hq true --apply-custom-presets false \
    images/Sweep_sRGB_Linear_Half_Zip_01.tif xmps/<name>.xmp expected/<name>.png \
    --core --disable-opencl --library :memory: \
    --conf host_memory_limit=8192 --conf resourcelevel=reference \
    --conf worker_threads=4 -t 4 \
    --conf plugins/lighttable/export/pixel_interpolator=lanczos3 \
    --conf plugins/lighttable/export/pixel_interpolator_warp=bicubic \
    --conf plugins/lighttable/export/iccintent=0
```

Double-check the new `expected.png` is actually correct (visually, or via
`--pristine`) before committing it — never regenerate blindly to make a
failing test pass.
